# Pointers: reaching a variable through its address

[00:00:05](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=5s) This lesson builds a pointer from ordinary variable reads and writes. You will first change an integer by its name, then obtain its address, and finally read and change the same integer through that address. The closing experiment explains why the pointer's target type matters: changing one byte of an integer can leave the rest of its old value behind.

The terms you will need are:

- **Memory cell, byte, and bit:** a cell in the diagrams represents a byte of storage. On the demonstrated machine, a byte contains eight bits, each either 0 or 1. **Binary representation** means the pattern of bits used to encode a value.
- **Variable, value, and assignment:** a variable names an object with storage; its value is the data currently stored there. Its **lifetime** is the period during which that object exists. An assignment replaces that data. A **declaration** gives a variable its type and name; **initialization** supplies its starting value.
- **Type and `int`:** a type determines how data is represented and which operations are allowed. `int` is the integer type used here, occupying four bytes on the demonstrated machine.
- **Output stream:** `std::cout` receives values for display through `<<`. `std::endl` ends the line and flushes the output.
- **Address, pointer, and pointee:** an address identifies a location in memory; a pointer stores an address value; the pointee is the object reached through it. `int*` means pointer to `int`.
- **Address-of and dereference:** unary `&` obtains an object's address. Unary `*` follows a pointer and gives access to its pointee.
- **Hexadecimal:** base-16 notation, using digits 0–9 and A–F; `0x` marks a hexadecimal number in the displayed addresses.
- **Virtual memory:** the operating system maps the program's addresses to underlying physical memory. **Address randomization** can change those addresses between program runs.
- **Alignment:** a type can require its storage to begin at a suitably divisible address. Empty-looking space between objects is not automatically part of either object's value.
- **Byte type and type checking:** `uint8_t` is an unsigned eight-bit integer type, when provided, with values 0–255. The **compiler**, which translates source code into an executable program, rejects ordinary assignments between incompatible pointer types.
- **Cast and little-endian order:** a cast explicitly requests a type conversion. A **C-style cast** writes the destination type in parentheses before its operand; **`reinterpret_cast`** is C++ syntax for an explicit reinterpretation. **`unsigned char`** is an unsigned character type permitted for byte access. A type **alias** is another name for the same type. Little-endian order places the least significant byte of a multi-byte integer at its lowest address.
- **Undefined behavior:** an operation for which C++ specifies no required result; accessing an object through an inappropriate type or outside its storage can cause this.

## Why a byte pointer is a different type

[00:10:47](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=647s) The **pointee type** tells the program which kind of object an access expects. The lesson contrasts a four-byte `int` with **`uint8_t`**, an unsigned eight-bit integer with range 0–255. On the demonstrated machine it occupies one byte.

## Casting to a byte pointer

[00:15:35](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=935s) The lesson now deliberately bypasses the ordinary pointer-assignment check with a **cast**, an explicit request to convert a value to another type. [00:15:44](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=944s) It interprets an integer's address as a byte pointer, so access through that pointer touches one byte instead of a whole integer.

A simplified reconstruction of the cast experiment is:

```cpp
int i = 15;
int* iad = &i;
std::uint8_t* byte = (std::uint8_t*)iad;
*byte = 8;
std::cout << i << std::endl;
```

The parenthesized type in `(std::uint8_t*)iad` is the C-style cast shown by this reconstruction. It changes the pointer's interpretation; it does not convert the stored integer into a new one-byte object.

[00:16:06](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=966s) After the byte write, the recorded small-value experiment reads back `8`. [00:16:16](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=976s) The explanation depends on **little-endian order**: the least significant byte is at the lowest address, which is the byte reached first. Starting from the small value 15, the other integer bytes are zero, so replacing the low byte with 8 makes the whole integer read as 8.

A cast alone does not make arbitrary typed memory access valid. C++ specifically permits access to an object's representation through `unsigned char`; the video's `uint8_t` approach relies on that type being an alias, another name for the same type, of `unsigned char` on its implementation. This distinction follows the [C++ object-access rules](https://eel.is/c++draft/basic.lval#11) and [reinterpretation rules](https://eel.is/c++draft/expr.reinterpret.cast). For an explicitly byte-oriented version of the same reconstruction:

```cpp
unsigned char* byte = reinterpret_cast<unsigned char*>(iad);
*byte = 8; // changes one representation byte, not an entire int
```

Here `unsigned char` is the byte-access type and `reinterpret_cast` is the explicit pointer reinterpretation syntax. This spelling clarifies the correction; it is not claimed as the exact spelling in the recording.

## Why 500 becomes 264

[00:16:33](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=993s) An integer larger than 255 needs more than one eight-bit byte. The demonstration changes the initial integer to 500, leaving a nonzero higher byte before writing the low byte:

```cpp
int i = 500;
unsigned char* byte = reinterpret_cast<unsigned char*>(&i);
*byte = 8;
std::cout << i << std::endl; // 264 on the demonstrated layout
```

This sample reconstructs the recorded experiment using the explicit byte-access type described above. [00:16:49](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=1009s) The output is `264`, rather than `8`.

On the demonstrated four-byte, little-endian layout, follow the bytes in increasing address order:

1. `500 = 1 × 256 + 244`, so its bytes are `244, 1, 0, 0`.
2. The byte pointer reaches only the first byte.
3. Writing 8 changes them to `8, 1, 0, 0`.
4. Reading the complete `int` yields `1 × 256 + 8 = 264`.

The higher byte retained part of the original 500. The write did not clear it. “Spilling into the next byte” describes how the multi-byte `int` represents a larger value; assigning an oversized value to an unsigned one-byte integer does not write past that byte into its neighbor.

<details>
<summary>Why did the earlier write produce 8, but this one produce 264?</summary>

The earlier integer had zero in all higher bytes. The integer 500 had 1 in the next byte, and the one-byte write left that 1 unchanged.

</details>

## Why the next result is 257

[00:17:45](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=1065s) The discussion uses 256 to make the boundary especially clear. It is the smallest nonnegative integer that needs more than one eight-bit byte. Its little-endian representation begins `0, 1`.

[00:18:05](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=1085s) A clearer reconstruction of the final low-byte change is:

```cpp
int i = 256;
unsigned char* byte = reinterpret_cast<unsigned char*>(&i);
*byte = 1;
std::cout << i << std::endl; // 257 on the demonstrated layout
```

The same result follows if the preceding 500 example's higher byte remains 1 and its low-byte write changes to 1. [00:18:05](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=1085s) The demonstrated result is `257 = 256 + 1`. Immediately before this, at [00:18:02](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=1082s), the instructor notices that the changed program had not been recompiled. The corrected result follows recompilation: running the old executable does not test a source-code edit.

[00:18:11](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=1091s) The byte write changes only the first of the four integer bytes. [00:18:15](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=1095s) The other bytes stay as they were. Replacing one byte does not carry into, increment, or reset its neighbors; this is different from performing arithmetic on the complete integer.

<details>
<summary>If the higher byte stays 1 and the low byte becomes 15, what whole number results?</summary>

On this layout, `256 + 15 = 271`. The retained high byte contributes 256 regardless of the new low-byte value.

</details>

## Returning to whole integer writes

[00:18:23](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=1103s) The byte-cast experiment is for understanding representation, not something the lesson recommends using in everyday integer assignments. Work with the integer through its proper integer type.

[00:18:44](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=1124s) Remove the byte reinterpretation and return to an `int*`:

```cpp
int i = 500;
int* iad = &i;
*iad = 8;
std::cout << i << std::endl; // 8
```

[00:19:01](https://www.youtube.com/watch?v=859Y0Q8pyLg&t=1141s) Since `iad` is a pointer to `int`, the assignment replaces the entire integer value. On the demonstrated machine that writes the integer across all four bytes; it leaves no retained high part of 500. The address in `iad` still identifies the same `i`.

The lesson's central distinction is now visible: `iad` supplies an address, while `*iad` gives access to the integer at that address. The pointee type determines what kind of object that access expects.
